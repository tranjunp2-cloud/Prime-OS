Rebuild Demand Hub into Demand Dashboard

Demand Dashboard phải trở thành màn hình đầu tiên của Demand: nắm toàn bộ tình trạng Sources, MDEC, Campaigns, Content & Social, Leads/RFQs, Re-engage bằng chart, diagram, infographic, quick links và priority actions. Mục tiêu là người dùng nhìn 10-30 giây là biết Demand đang khỏe hay bị nghẽn, nên mở function nào tiếp theo.

Boundary Not BI

Overview + action accelerator, không phải report builder.

1. Scope Challenge

Hard-mode scope: rebuild the entry point and visual information architecture, not a configurable analytics product.

Plan only No code changes in this step

Ship now

  • Rename visible product copy from Demand Hub to Demand Dashboard.
  • Move Dashboard to the first/top Demand function in navigation.
  • Show function cards before generic KPIs: MDEC, Sources, Campaigns, Content & Social, Leads/RFQs, Re-engage.
  • Add chart/infographic layout: function readiness, demand funnel, source mix, outcome readback, guardrail rail.
  • Keep all quick links to existing Demand routes and Sources child function routes.

Defer

  • Custom dashboard builder or draggable widgets.
  • Real-time streaming metrics.
  • New chart library for funnel visualization.
  • Deep attribution modeling or final ROI claims.
  • New backend analytics contracts unless implementation hits a hard limit.
  • MDEC execution details that belong inside MDEC itself.

3. Product Positioning

Demand Dashboard is the command surface for the full Demand suite, not a sub-module page.

Primary promise

What is happening across Demand, what needs attention, and where should I go next?

First-screen answers

  • Are we generating enough demand?
  • Which channels or sources are working?
  • What is blocked or needs action?
  • Where should I click next?

Target users

  • Demand owner: pipeline health and weak spots.
  • Operator: today’s tasks and quick entries.
  • Executive: fast read on contribution, trend, and risk.

Responsive rules

  • Desktop: 5 function cards, 2-column dashboard grid, charts height around h-64.
  • Tablet: function cards 2 columns, charts stack under queue.
  • Mobile: cards become compact rows, charts degrade to readable bar lists if labels crowd.

  • Each chart needs an sr-only or visible text summary.

7. Demand Dashboard Data Model

Keep calculations in a derived read model so the page remains a presentation layer.

interface DemandDashboardSnapshot {
  generatedAt: string;
  kpis: {
    activeCampaigns: number;
    sourceQualityScore: number;
    openLeads: number;
    openRfqs: number;
    responseBacklog: number;
    reengageEligible: number;
    blockedGuardrails: number;
    outcomeOrders: number;
    outcomeRevenue: number;
    leadToOrderRate: number;
  };
  functions: DemandFunctionSummary[];
  blockers: DemandBlocker[];
  nextMoves: DemandNextMove[];
  outcomeReadback: DemandOutcomeReadback[];
}
interface DemandFunctionSummary {
  id: 'mdec' | 'sources' | 'campaigns'
    | 'content-social' | 'leads-rfqs' | 're-engage';
  label: string;
  href: string;
  readiness: number;
  status: 'ready' | 'watch' | 'blocked';
  primaryMetric: string;
  nextAction: string;
  blockers: string[];
}

interface DemandNextMove {
  id: string;
  priority: number;
  functionId: DemandFunctionSummary['id'];
  title: string;
  evidence: string;
  href: string;
  owner: string;
  blockedBy: string[];
}
Recommended file boundary

Add prime-os-phase-1/app/src/lib/prime/demand-dashboard.ts with helpers like buildDemandDashboardSnapshot(snapshot). Let PrimeDemandHubPage consume the derived dashboard snapshot instead of re-deriving KPIs inline.

8. Business Rules and Boundaries

Rules prevent the Dashboard from making unsafe scale recommendations or claiming ownership of other suites.

9. Cross-Function Workflows

Dashboard links the suite together without absorbing each product’s operational depth.

Operator flow

  1. Open Demand Dashboard from first Demand nav item.
  2. Read command bar: readiness, guardrails, open moves.
  3. Scan function cards to identify blocked or ready function.
  4. Use readiness chart and funnel infographic to understand where the flow is stuck.
  5. Open priority queue item or function quick link.
  6. Return to Dashboard for outcome readback.

System flow

  1. Build dashboard snapshot from getPrimeSnapshot() and buildDemandSources().
  2. Compute function readiness and blockers.
  3. Rank next moves: guardrail, source, campaign, RFQ, re-engage.
  4. Render charts and text fallbacks from one read model.
  5. Preserve routes to existing Demand pages.

10. Implementation Phases

Phased so cook can stop after a useful MVP if needed.

Phase 1

Rename and promote Demand Dashboard

Change visible label from Demand Hub to Demand Dashboard and ensure it is the first Demand function.

Update prime-navigation.ts label to Demand Dashboard.
Keep /demand and /demand/hub routes compatible.
Replace visible copy in PrimeDemandHubPage.
Verify breadcrumbs/search/sidebar do not show stale Demand Hub label.
Phase 2

Create DemandDashboardSnapshot read model

Move dashboard calculations out of the component and reuse Sources read model.

Add prime-os-phase-1/app/src/lib/prime/demand-dashboard.ts.
Derive function summaries, KPIs, blockers, next moves, readiness chart data, funnel data, and outcome readback.
Add tests for readiness, blocker ranking, route coverage, and empty snapshot handling.
Do not mutate snapshot or source-of-truth stores.
Phase 3

Rebuild first viewport IA

Put the command bar and Demand function cards at the top, before the priority queue.

Add command bar with operating answer, readiness progress, guardrails, and CTAs.
Add six function cards: MDEC, Sources, Campaigns, Content & Social, Leads/RFQs, Re-engage.
Each function card is a native link with icon, status, metric, next action, and route.
Keep card copy short; move explanatory detail into tooltip/info patterns if needed.
Phase 4

Add charts and infographics

Use visual aids to make the dashboard understandable without overbuilding analytics.

Add function readiness bar chart using ChartContainer and Recharts.
Add CSS funnel infographic for Source -> Campaign -> Content -> Lead/RFQ -> Outcome.
Add outcome readback stacked bar chart by campaign.
Add text fallback summaries for chart accessibility.
Phase 5

Restructure priority queue, guardrails, and quick links

Make action obvious, while preserving all current Demand destinations.

Rank priority queue by severity, owner, evidence, and blocker state.
Add guardrail rail beside queue on desktop and below queue on mobile.
Add quick links for Sources child functions and major Demand routes.
Prevent chart/card overload by making outcome table supporting evidence below charts.
Phase 6

QA, responsive, and route validation

Validate the new Dashboard as the Demand entry point.

Run npm run test -- demand-dashboard demand-sources or targeted vitest files.
Run npm run lint and npm run build:dev.
Playwright smoke /demand, /demand/hub, and key Demand links.
Check 1440px, tablet, and 390px mobile for no horizontal overflow and readable charts.

11. Acceptance Criteria

Definition of done for implementation.

Product acceptance

  • Demand nav shows Demand Dashboard first.
  • Page H1 and visible copy use Demand Dashboard, not Demand Hub.
  • First viewport answers: health, working sources/channels, blockers, where to click next.
  • Every major Demand function has visible summary and quick link.
  • At least three visual aids exist: readiness chart, funnel/flow infographic, outcome readback chart.
  • Priority queue remains action-oriented with owner, evidence, route, and severity.

Engineering acceptance

  • Dashboard uses a derived read model, not scattered formulas in JSX.
  • No new chart library introduced.
  • Existing routes remain compatible.
  • Empty data states do not look broken.
  • Charts have labels and text fallback; color is not the only status signal.
  • Desktop/mobile smoke tests pass or any blocker is documented.
