Product Operation Agent cho hệ thống vận hành bằng Kanban dashboard

Hướng phù hợp là xây một lớp AI-assisted operating execution layer: Kanban không chỉ là task board, mà là cockpit để PrimeOS phát hiện tín hiệu, gom bằng chứng, mở quyết định, điều phối owner, xin duyệt, thi hành hành động đã được approve và ghi audit xuyên Demand, Ecom/COS, Finance, Customer và Intelligence.

Recommendation

A

Build as a new Intelligence product

Không replace Consulting Agent ngay. Tạo Product Operation Agent như control-plane product, reuse board primitives hiện có rồi mở rộng persistence/guardrails.

MVP wedge: weekly operating review Owner: Intelligence suite Execution: approved actions only

Decision

Chọn hướng “Operator, not boss”. Agent được quyền đọc tín hiệu, chuẩn bị work card, đề xuất next action, kéo evidence và route approval. Agent không tự thay đổi source-of-truth quan trọng nếu chưa có human confirmation. Đây là hướng khớp với PrimeOS hiện tại vì board Intelligence đã nói rõ “source truth remains owned by Demand, Customer, Ecom/COS, and Finance”.

Product Shape

Recommended IA for Product Operation Agent in PrimeOS.

Positioning

PrimeOS Product Operation Agent is the operating cockpit that converts system signals into governed execution cards across all suites.

  • Not a passive dashboard.
  • Not autonomous business decision maker.
  • Not another Trello/Jira clone.
  • It is the layer that prepares, routes, and executes approved operating work.

Core promise

“Every system signal becomes a clear operating card with owner, evidence, policy, next action, approval state, and audit trail.”

  • Detect drift and blockers.
  • Make work visible.
  • Limit WIP by owner and lane.
  • Escalate stale or blocked work.
  • Execute only after approval.

Operating Kanban Model

Board này là heart của product. Card không phải task thường; card là operating commitment.

Signal

Metric drift, SLA breach, stock risk, campaign anomaly, lender blocker, customer identity alert.

Auto card Evidence source + severity + source owner

Triage

Agent groups duplicates, checks freshness, assigns likely owner and recommended route.

Policy Must have owner + source link

Decision Needed

Human must choose go/review/hold/no-go or approve a suggested action.

Approval No mutation before confirm

In Progress

Approved workflow is running or owner is actively doing the work.

WIP Limit per owner and suite

Waiting

Blocked by external response, missing document, delayed stock, customer reply, lender feedback.

SLA Aging threshold triggers escalation

Done

Action completed and written back to the owning route or read-model.

Audit Completion proof required

Learning

Outcome captured for next operating review, playbook, forecast, or agent eval.

Memory Close loop into PrimeOS context

Implementation Roadmap

Phased plan sized for PrimeOS current codebase.

Phase 1

Product registration

Add Product Operation Agent to primeNavigation, route it in App.tsx, and expose floors in Product Settings.

Phase 2

Operating card model

Create seed/read-model builder from getPrimeSnapshot(). Generate cards from KPI drift, blockers, escalations, finance readiness and CRM identity alerts.

Phase 3

Kanban cockpit

Build OperatingKanbanBoard from existing drag board patterns. Add WIP badges, aging, severity, owner, source route and card drawer.

Phase 4

Agent queue

Add action proposals: draft memo, open owner route, request approval, send follow-up, mark blocked, mark complete. Keep all write actions behind explicit confirm.

Phase 5

Audit and persistence boundary

Start local audit like Consulting Agent. Then define backend resource for cards/events when the UX is validated.

Phase 6

Validation

Smoke all floors, test route matching, test card generation, test move audit, test approval gates, and run screenshot QA for desktop/mobile.

Acceptance Criteria

Concrete checks for the first implementation pass.

Product behavior

  • Pass Product Settings shows Product Operation Agent under Intelligence.
  • Pass Route opens from Product Settings, global search, and sidebar.
  • Pass Board shows cards from at least four suites: Demand, Ecom/COS, Finance, Customer.
  • Pass Dragging a card updates lane and appends audit event.
  • Pass Risky action requires approval before state mutation.

Engineering checks

  • npm run build:dev passes.
  • Navigation tests cover the new route and floors.
  • Seed data tests cover card generation from snapshot.
  • Playwright smoke covers board drag, drawer, filters, and mobile overflow.
  • No new dependency unless a durable workflow engine is explicitly chosen.

Risks

Risks that should shape implementation decisions.

Generic board trap

If cards are just todos, product loses differentiation. Mitigation: every card must carry metric, evidence, policy, source route and audit trail.

Autonomy trust gap

Users will reject silent mutation. Mitigation: agent proposes and prepares; humans approve material actions.

Persistence gap

Current Consulting Agent board is local state only. Mitigation: MVP can prove UX locally, but phase 2 needs backend card/event resource.
